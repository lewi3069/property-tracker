# Faster motion switches (0.2.17)

The eligible native thirteen-camera TV motion profile now defaults to a five-second minimum camera hold and a one-second delay before expanding for additional active cameras. The fifteen-second all-clear return and lower-count shrink delays remain unchanged. The first detection remains immediate. Uncheck **Faster motion switches** in Screen layout to restore the previous ten-second hold, two-second expansion and ordinary stream replacement. Manual Grid/Pin, phone, floating video and other playback profiles retain their policy.

When the selected camera already has healthy live grid video, its tile and native video view remain attached while the hardware main stream connects underneath. The live grid picture enlarges immediately; the main view replaces it only after an actual first-rendered-frame callback. No screenshot or frozen-frame placeholder is used. If the main stream fails while the retained grid remains healthy, the app reuses that grid connection and its frame-health state. An unavailable or stale grid uses ordinary startup instead, so cold cameras still have connection and buffering delays. This does not shorten the main stream's own startup time.

The live-preview handoff requires the normal native TextureView output. The optional SurfaceView experiment and other backends keep ordinary replacement. Only one hardware main stream is allowed. A temporary preview is limited to the existing reduced motion layouts, keeping the target wall plus preview within the thirteen-stream budget. Old main players retire before a new main starts. The shared two-start admission limit and native-release barrier remain intact. Cancellation, another camera selection, backgrounding and shutdown close retained previews; a successful main first frame closes its preview once. Native tiles continue avoiding an unused Media3 view hierarchy except while that one tile upgrades.

This preserves high-resolution main-stream selection and existing camera encoders, catalogs, identities and MQTT settings. The new configuration flag does not change the saved camera count. Older settings without the flag use the faster response on eligible profiles; turning it off is persisted. Extra temporary video output and view resizing still require device validation, especially while native-memory stability remains unresolved. No general memory fix or instant cold-stream startup is claimed.

All 195 host tests passed (181 TV/core and 14 phone), both debug APKs built, lint reported zero errors, and package/SDK/native-library/original-signature guards passed. Tests cover faster and Calm timing boundaries, unchanged quiet restoration, saved-setting compatibility, retention of the same tile and native view, old-main retirement before new-main admission, release only after the real first-frame callback, buffering before that frame, fallback without a grid reconnect, cancellation and replacement cleanup, stale video and unsupported preview outputs. Host tests cannot establish the physical compositor behavior or sustained memory stability. Device visual confirmation remains pending. No APK is published as a public release.
