# AFTKM graphics-service restart and playback budget

An AFTKM Fire TV running API 30 was reported to have restarted while using a nine-camera layout, with some feeds failing to load. Its retained crash buffer shows a native SIGSEGV in the vendor hardware-composer service, including `hwcomposer.mt8696.so` and `HWCDispatcher::present`. A matching `SYSTEM_RESTART` record follows. Kernel uptime remained above eight days, so this evidence supports a graphics/Android runtime restart rather than a recent kernel reboot. It does not establish which client or condition caused the vendor fault.

All 14 saved H.264 grid streams rendered a first frame when rechecked individually on the affected device. This verifies those addresses, credentials and streams at the time of testing; it does not establish their simultaneous capacity. A decoder/compositor resource issue remains a plausible explanation for feeds failing together.

Version 0.2.2 applies a conservative four-camera budget to AFTKM. Startup clamps and saves an existing nine-camera preference before creating players. Fullscreen grids and MQTT layout commands share the same limit. The full catalog remains available through View and fullscreen browsing. The existing AFTT two-camera and AFTMM/low-RAM four-camera budgets remain in place; Shield keeps its larger layout choices.

This reduces simultaneous video surfaces. It does not repair the vendor driver or prove that nine surfaces caused this crash. SurfaceView playback, floating H.264 compatibility mode, stream paths and broker configuration are unchanged.

Validation: all 88 TV/core tests passed, including a rendered-wall regression for a saved nine-camera request, an MQTT nine-camera request, fullscreen layout and access to a camera outside the four-tile wall. Lint reported zero errors and 29 warnings. The signed APK keeps the existing package/key and API 22 minimum.

After installation, a 302-second observation of the normal four-camera viewer recorded 20 samples. All four video surfaces advanced between every sample. The app, codec, hardware-composer, SurfaceFlinger and system-server PIDs remained unchanged, as did the kernel boot ID. App RSS ranged from about 55 to 71 MiB and ended below its starting value. This is a short functional result, not proof of sustained reliability or physical-TV image quality. Nine-camera playback was not reproduced.

A separate brief activity trial brought two 1536 × 576 H.264 streams into the four-tile wall. Both rendered first frames, all four tiles reported Live, and expiring MQTT events restored the original overview. The app and system graphics PIDs remained unchanged, MQTT stayed connected, and the inspected logs contained no new playback-failure, stall or native-crash records. No persistent automation or camera setting was changed by the trial.
